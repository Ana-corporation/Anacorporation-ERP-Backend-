================================================================================
0. GLOBAL CONTRACT (ALL ADMIN APIs)
================================================================================

RESPONSE ENVELOPE (required for every endpoint)
-----------------------------------------------
  {
    "success": true,
    "message": "Success",
    "data": { ... } | [ ... ] | null,
    "timestamp": "ISO-8601"
  }

  On error:
  {
    "success": false,
    "message": "Human readable error",
    "data": null,
    "errors": [ { "path": ["fieldName"], "message": "..." } ],
    "timestamp": "..."
  }

  Frontend uses unwrap() -> reads envelope.data only.

AUTH HEADERS (every authenticated call)
---------------------------------------
  Authorization: Bearer <accessToken>
  Content-Type: application/json
  x-company-id: <activeCompanyId>     (optional but sent when available)
  Cookie: withCredentials=true        (refresh_token httpOnly)

CASING
------
  Preferred API JSON: camelCase  (matches current GET /companies)
  Frontend UI state:  snake_case after mapping
  Backend may return camelCase; FE maps fields (see companies-api.ts).

ID TYPES
--------
  Prefer stringified IDs in JSON (BigInt-safe): "15"
  Frontend currently coerces companyId with Number() for Redux — keep IDs
  stable and unique. Prefer consistent string IDs everywhere if possible.

--------------------------------------------------------------------------------
A1. LIST COMPANIES                                          [LIVE]
--------------------------------------------------------------------------------
  Method:  GET
  Path:    /companies
  Query:
    page=1
    limit=200
    search=acme          (optional)
    status=active        (optional: trial|active|suspended|cancelled)

  Headers: Bearer + optional x-company-id

  Response data:
  {
    "items": [
      {
        "companyId": "15",
        "companyCode": "DEMO_ACME",
        "name": "Demo Acme Corp",
        "legalName": "Demo Acme Corporation Ltd",
        "domain": "demo-acme.com",
        "email": "admin@demo-acme.com",
        "phone": "+91-9876543210",
        "city": "Chennai",
        "country": "IN",
        "logoUrl": null,
        "status": "trial"
      }
    ],
    "total": 1,
    "page": 1,
    "limit": 200,
    "totalPages": 1
  }

  Logic:
    - Hide/exclude PLATFORM company from tenant UI list (FE filters companyCode PLATFORM)
    - List should support pagination for large fleets
    - Enrichment (plan name, user count, module progress) can be:
        Option A: included as summary fields in list OR
        Option B: FE loads separately (prefer Option A for list cards)

  REQUESTED EXTRA SUMMARY FIELDS (nice-to-have on list items):

    "planName": "Demo Starter",

################################################################################
# SECTION J — ONBOARDING PIPELINE LOGIC (FRONTEND EXPECTS)
################################################################################

Company detail shows checklist stages. Backend should enable these states:

  1. Profile complete
       company has name + companyCode (+ preferably email)
  2. Subscription assigned
       active OR trial subscription exists
  3. Organization started
       at least 1 branch AND 1 department
  4. Modules enabled
       at least 1 company module isActive=true
  5. Roles & users ready
       at least 1 non-system-or-any role AND >=1 membership user
  6. Go live
       company.status == active  (and subscription healthy)

Backend does NOT need a special "onboarding" API if FE can derive from
GET company detail aggregates. Prefer one detail endpoint that returns:

  GET /companies/:id/setup-summary
  {
    "company": { ... },
    "subscription": { ... } | null,
    "counts": {
      "branches": 1,
      "departments": 2,
      "designations": 3,
      "warehouses": 1,
      "roles": 4,
      "users": 5,
      "activeModules": 6,
      "entitledModules": 6
    }
  }

Optional but very useful for Overview tab.

0. FINAL PRODUCT DECISIONS (LOCKED)
================================================================================

  1. MULTI-TENANT MODEL
     - Shared PostgreSQL database (NOT one DB per company)
     - Every tenant row uses company_id
     - Login: companyCode + employeeCode → JWT with companyId
     - APIs: /api/v1/companies/{companyId}/...

  2. CUSTOM FIELDS STORAGE
     - Do NOT ALTER vendors table for new fields
     - Definitions → table: custom_field_definitions
     - Values     → table: custom_field_values
     - Vendor also has metadata JSON for SAP-style hardcoded tabs
     - Dynamic UDFs use customFields map (NOT metadata)

  3. ADMIN CREATES FIELDS DIRECTLY
     - NO request / approve / reject workflow (skipped for now)
     - Company ADMIN creates field → ACTIVE immediately
     - Normal users only fill values on Vendor form
     - Approval workflow may be added later as optional enterprise feature

  4. MODULE SCOPE
     - entityType = vendor ONLY right now
     - Customer / Employee / other modules = later (separate handoff)

  5. FORM UX GOAL
     - Place custom fields into existing Vendor tabs via sectionKey
     - End user should see one form (standard + custom mixed by section)
     - Not a separate forever-only "Custom Fields" dump tab (use sectionKey)


1. WHAT IS ALREADY BUILT (BACKEND)
================================================================================

  Database
    - custom_field_definitions  (field setup)
    - custom_field_values       (answers per vendor)

  Permissions
    - custom_fields:view
    - custom_fields:create
    - custom_fields:edit
    - custom_fields:delete
    - Seeded on PLATFORM_OWNER + DEMO_ACME ADMIN

  Admin APIs (direct create — no PENDING)
    GET  /api/v1/custom-fields/meta/modules
    GET  /api/v1/custom-fields/meta/modules/vendor/sections
         → sections[] + reservedFieldNames[]

    GET  /api/v1/companies/{companyId}/custom-fields?entityType=vendor
    GET  ...?entityType=vendor&groupedBySection=true
    GET  .../custom-fields/{fieldId}
    POST .../custom-fields          (creates ACTIVE definition now)
    PATCH .../custom-fields/{fieldId}
    DELETE .../custom-fields/{fieldId}   (soft deactivate)

  Vendor form / values
    GET  /api/v1/companies/{companyId}/entities/vendor/form-schema
         → fields with sectionKey, isFilterable, validation, options, …
    GET/POST/PATCH /api/v1/companies/{companyId}/vendors
         → customFields: { "vendorTier": "preferred", ... }
    GET  .../vendors?includeCustomFields=true
    GET  .../vendors?cf.vendorTier=preferred   (filterable only)

  Create behavior
    - displayName required
    - fieldName optional → auto from displayName (factoryCapacity)
    - sectionKey optional → default/normalize to custom if unknown
    - Reserved names rejected (paymentTerms, email, name, …)
    - Duplicate label/key → 400
    - Dropdown requires options[]
    - Unsupported types (lookup/file/formula…) → 400 not implemented

5. metadata vs customFields
================================================================================

  metadata       = FE hardcoded SAP-style tabs (payment, bank, …)
  customFields   = dynamic admin-defined UDFs from form-schema

  Keep BOTH. Do not put same key in both namespaces.
  Legacy demo CF paymentTerms is deactivated (collides with metadata).

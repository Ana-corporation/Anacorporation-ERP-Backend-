PURCHASE ORDER MODULE - LOW-LEVEL DESIGN (LLD)
==============================================
Version : 1.1  (09-Nov-2026)
Based on: "Purchase Order Module LLD & UI Specification" v1.0 (08-Nov-2026)
Change  : v1.0 was technology-neutral. v1.1 maps it to the ANA ERP stack,
          the modules that already exist, and the screens to build.
          Business rules are unchanged unless marked [v1.1].
Status  : For review. Nothing built.


==========================================================================
1. PURPOSE
==========================================================================
Two purchasing flows:
  (1) Production purchase - material shortages from a machine order
      (machine + released BOM + quantity) -> Purchase Requirements ->
      buyer makes one or more POs.
  (2) Stock replenishment - buyer buys for stock without a shortage;
      approval is always required.

Core rule: an order never creates a supplier PO directly. System expands
the BOM, checks usable stock, creates Purchase Requirements for the
shortage only, and the buyer converts them into POs.

4. CONFIRMED BUSINESS REQUIREMENTS  (from v1.0)
==========================================================================
  BR-01  An order usually has one machine type, qty > 1; may have several
         machines. Each machine line uses its own BOM; component qty x
         machine qty.
  BR-02  Each machine has its own BOM (machines + boms - exists).
  BR-03  Check required qty against usable stock.
  BR-04  Shortages become internal Purchase Requirements; no automatic
         supplier PO.
  BR-05  Requirements from several orders may be combined - buyer's choice;
         source traceability kept.
  BR-06  Buyer may change purchase qty, with reason; original shortage
         kept.
  BR-07  Partial receipts: many GRNs per PO.
  BR-08  Replenishment PO without shortage; approval mandatory.
  BR-09  Supplier email tracked: attempts, retries, manual resend.
  BR-10  Only accepted goods increase usable stock.

  In scope : requirements, consolidation, PO draft/approval/issue/cancel/
             close, supplier PDF + email tracking, GRN with partial and
             accepted/rejected qty, stock update, enquiry, reports, roles.
  Out      : supplier invoice / AP / payment, 3-way match (Finance LLD),
             production execution, supplier portal / EDI, forecasting.


==========================================================================
5. END-TO-END FLOW
==========================================================================
5.1 Production purchase
  1. Planner picks machine (BS500 or BS500-SO00045), its RELEASED BOM,
     quantity, warehouse and required date.            [v1.1: no SO yet]
  2. System expands the BOM x quantity (existing BOM requirements logic).
  3. System reads usable stock per component.
  4. System creates Purchase Requirements for net shortages only.
  5. Buyer reviews; optionally combines; creates PO draft(s).
  6. Buyer submits -> approver approves / rejects.
  7. Approved PO is issued -> PDF + email (status tracked separately).
  8. Supplier delivers -> one or more GRNs (Material Inward).
  9. Accepted qty -> usable stock; rejected/QC-pending -> not usable.
 10. PO line + header status recalculated until fully received / closed.

5.2 Stock replenishment
  1. Buyer: New PO, type = Stock Replenishment.
  2. Picks warehouse, supplier, items, qty (shows current stock).
  3. Enters reason (mandatory), submits.
  4. Approval always required.
  5. Same issue / GRN / stock flow as above.

5.3 Picture
  Machine + BOM + qty --> expand --> check stock
                                   /            \
                            enough               shortage
                               |                    |
                           (production)     Purchase Requirement
                                                    |
                                          buyer review / adjust
                                           /                 \
                                   separate PO         combine (optional)
                                           \                 /
                                             PO Draft -> Submit
                                                    |
                                          Approve / Reject
                                                    |
                                         Issue (PDF + email)
                                                    |
                                      GRN (partial, many) -> QC
                                                    |
                                    accepted qty -> stock IN
                                                    |
                                        PO status recalculated

6. FUNCTIONAL DESIGN
==========================================================================
6.1 Material requirement (shortage) calculation
  - Machine qty: positive whole number.
  - BOM: only the RELEASED current BOM of the machine (STANDARD, or the
    CUSTOMER BOM of a customised machine). [v1.1]
  - Required qty = BOM qty per machine x machine qty (scrap factor:
    OD-03, off in phase 1).
  - Materials = SUB lines + MAIN lines without SUBs (same rule as the BOM
    "Requirements" button). MAIN assemblies are not purchased. [v1.1]
  - Store a snapshot: BOM id, number, version, lines used. Later BOM
    revisions must not change the snapshot.
  - Several machine lines: calculate each, then sum by item + warehouse
    + required date.

6.2 Usable stock
  Available = on hand - reserved - blocked/quarantine.
  Unreceived PO qty is NOT counted.
  [v1.1] We do not track reserved / blocked yet, so phase 1:
         Available = stock_balances.quantity in the chosen warehouse.
         QC-pending GRN qty is not in stock_balances, so not counted.
  Shortage = max(0, required - available).

6.3 Purchase Requirement (internal, not sent to supplier)
  Requirement No    PR-000001 (number series)
  Source type       SHORTAGE or REPLENISHMENT
  Source            machine, BOM no + version, (later: SO + SO line)
  Item, warehouse, required qty, requested date
  Suggested vendor  optional (item preferred vendor / last PO)
  Converted qty     how much is already on POs
  Open qty          required - converted
  Status            DRAFT, PENDING_REVIEW, APPROVED, PARTIALLY_CONVERTED,
                    FULLY_CONVERTED, CANCELLED
  Rule: the same open qty can never go onto two POs - conversion locks
        the requirement row (FOR UPDATE) and reduces open qty in the same
        transaction.

6.4 Review and optional consolidation
  - Filter by item, vendor, warehouse, date, machine/BOM, status.
  - Select one or many -> Create PO.
  - Combine only when vendor, currency, purchase UOM and ship-to
    warehouse match. System never forces combining.
  - One PO line may come from many requirements; each line keeps a
    source breakdown (which requirement, how much).
  - One requirement may be split across POs / vendors.
  - Buyer may order more or less than required:
      less  -> balance stays open on the requirement
      more  -> excess marked buyer-added; reason required
    Stored: original qty, ordered qty, variance, reason.

6.5 Purchase Order
  Header
    PO No              PO-000001 (number series)
    PO Type            PRODUCTION or REPLENISHMENT
    Vendor             active vendor (vendors)
    Vendor address / contact / email   snapshot at issue
    PO Date            today (editable with permission)
    Currency           vendor default; edit with permission
    Payment terms      vendor default; snapshot
    Delivery date      header default; line may override
    Ship-to warehouse  one per PO (OD-04)
    Buyer              logged-in user
    Vendor reference, internal notes, supplier notes
    Subtotal / discount / tax / freight / other / grand total   calculated
    Status             see 6.9
    Send status        NOT_SENT, QUEUED, SENT, FAILED
    Reason             mandatory for REPLENISHMENT
    Version            1, 2, ... (amendments)
  Lines
    Line no, item (part no + old part no), purchase description,
    purchase UOM (+ conversion to inventory UOM), ordered qty, unit price,
    discount, tax code / %, net / tax / gross, required date, warehouse,
    source allocation, received / accepted / rejected / outstanding qty.

6.6 Approval
  - REPLENISHMENT: always needs approval.
  - PRODUCTION: approval matrix (by type, amount, currency) - settings,
    not hard-coded (OD-01, OD-02).
  - Submit   : validate, freeze values, create approval task.
  - Approve  : approver, time, comment, version -> APPROVED.
  - Reject   : reason required -> REJECTED -> buyer edits / resubmits.
  - Pending  : no edit; Withdraw (if allowed) -> DRAFT.
  - After approval: commercial change = new version + re-approval.
  - Creator cannot approve own PO (setting, default off).

6.7 Supplier communication
  - PDF from the approved version only; stored (file_assets) for audit.
  - Email only after approval, to the contact snapshot on the PO.
  - Each attempt: recipient, time, status, error, retry count.
  - BullMQ job retries transient failures; after the last retry -> Email
    Failure Queue.
  - Manual resend = new attempt, same PO version, no new PO.
  - Email failure never undoes approval.

6.8 GRN (Material Inward)  [v1.1]
  GRN, QC and put-away screens already exist in Material Inward. The PO
  module feeds them:
  - GRN can pick only APPROVED / SENT POs, outstanding lines only.
  - Delivered > 0 and <= outstanding (over-receipt tolerance 0%, OD-06).
  - Accepted + rejected + QC-pending = delivered.
  - Batch / serial only for tracked items.
  - On posting: accepted qty -> usable stock IN (OD-12), rejected qty ->
    no stock, QC-pending -> quarantine (not usable).
  - Posting idempotent; posted GRN never deleted - reversal only.
  - After each GRN: PO line received / accepted / outstanding updated and
    PO status recalculated.

6.9 PO status
  DRAFT -> PENDING_APPROVAL -> APPROVED -> SENT -> PARTIALLY_RECEIVED ->
  FULLY_RECEIVED -> CLOSED
  REJECTED (back to buyer), CANCELLED (no new GRN; old receipts stay).
  Close with open qty needs permission + reason.
  Send status is a separate field (APPROVED + FAILED is valid).

13. ACCEPTANCE TESTS  (from v1.0; * = adjusted [v1.1])
==========================================================================
  AT-01  BS500 x 3, BOM motor qty 2 -> motor required 6.
  AT-02* Two machines with different BOMs -> each expanded, traced.
  AT-03* Required 10, on hand 12 -> no shortage (reserved/blocked not
         tracked in phase 1; full rule when reservations exist).
  AT-04  Covered by stock -> no requirement.
  AT-05  Two shortages same motor, combine -> one PO line, two sources.
  AT-06  Same, not combined -> two POs.
  AT-07  Shortage 7, ordered 10 -> 7 / 10 / variance 3 / reason.
  AT-08  Replenishment PO -> draft ok, approval before issue.
  AT-09  Issue unapproved PO -> blocked (PO_NOT_APPROVED).
  AT-10  PO 100, GRN 60 accepted -> stock +60, partially received.
  AT-11  GRN 40 more -> stock +40, fully received.
  AT-12  GRN 10: 8 accepted, 2 rejected -> stock +8 only.
  AT-13  GRN post sent twice -> one stock posting.
  AT-14  Email fails -> PO stays approved, attempt in S9.
  AT-15  Resend -> new attempt, same version, no new PO.
  AT-16  BOM revised after run -> old requirement snapshot unchanged.
  AT-17  Over-receive -> GRN_OVER_RECEIPT.
  AT-18  No approve permission -> 403, no change.
  AT-19* Two buyers convert the same requirement at once -> only open qty
         is converted; second gets PR_QTY_EXCEEDED.

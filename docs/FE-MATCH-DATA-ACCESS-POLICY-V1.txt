0) BIG PICTURE (for FE)
--------------------------------------------------------------------------------

  Role → Permissions     = WHAT the user can do   (unchanged; matrix only)
  Data Access Policy     = WHERE they can do it   (branch / department / warehouse)

  Permission Sets UI was removed on FE — BE APIs may still exist but FE
  should NOT call them. Day-to-day FE uses:
    - Roles matrix (role_permissions)
    - Access Policies tab + user drawer assignment


1) WHAT BE CHANGED RIGHT NOW (FE MUST MATCH)
--------------------------------------------------------------------------------

A) Access Policies create/update body — BREAKING vs older scopes[]

  OLD (do not send):
    scopes: [{ scopeType: "warehouse", scopeId: "3" }, ...]

  NEW (required):
    branchIds: string[]
    departmentIds: string[]
    warehouseIds: string[]
    code: string          ← required on CREATE (was optional before)

  Example CREATE:
    POST /companies/:companyId/data-access-policies
    {
      "code": "CHENNAI_PURCHASE",
      "name": "Chennai Purchase Access",
      "description": "Purchase data access for Chennai",
      "isActive": true,
      "branchIds": ["1"],
      "departmentIds": ["2"],
      "warehouseIds": ["3"]
    }

  Example UPDATE (any field optional; only send ids you want to change):
    PATCH /companies/:companyId/data-access-policies/:id
    {
      "name": "Chennai Purchase Access",
      "branchIds": ["1", "4"],
      "departmentIds": ["2"],
      "warehouseIds": ["3"]
    }


B) Access Policies response shape — BREAKING

  Response no longer returns scopes[].
  Each policy now returns:

    policyId, companyId, code, name, description, isActive,
    createdAt, updatedAt, deletedAt,
    branchIds: string[],
    departmentIds: string[],
    warehouseIds: string[]

  Update FE forms/tables/drawers to read branchIds / departmentIds / warehouseIds.


C) User policy assignment APIs

  Spec V1 (preferred):
    POST   /companies/:companyId/users/:userId/data-access-policies
           body: { "policyId": "..." }

    DELETE /companies/:companyId/users/:userId/data-access-policies/:policyId

  Legacy still works (current FE drawer can keep this until you migrate):
    PUT    /companies/:companyId/users/:userId/data-access-policies
           body: { "policyIds": ["...", "..."] }

  GET list (unchanged path):
    GET    /companies/:companyId/users/:userId/data-access-policies
           → assignments; nested policy uses NEW shape (branchIds etc.)

4) EMPTY SCOPE / BEHAVIOR FE SHOULD EXPECT
--------------------------------------------------------------------------------

  - Policy saved with empty branchIds + departmentIds + warehouseIds
      → means NO data access (not “all data”)

  - User with no policies assigned
      → no WHERE restriction (full org data for that permission)

  - User with one or more active policies
      → effective scope = UNION of all assigned policies
      → Items warehouse write out of scope → 403; FE toast via getApiErrorMessage

  -   Soft-deleted / inactive policies do not grant scope

  CREATE CODE UNIQUENESS (2026-08-13)
  - Duplicate create code no longer 409
  - BE appends _2, _3, … and returns the final code in the response
  - Update with colliding code still 409 (no silent rename)
  - Soft-deleted codes are reusable (delete renames stored code to free unique)


5) WHAT FE SHOULD NOT CALL / NOT BUILD
--------------------------------------------------------------------------------

  - Permission Sets UI / API clients (removed on FE; optional on BE)
  - Do not treat Data Access Policy as granting permissions
  - Do not invent per-branch role clones (e.g. “Purchase Manager - Chennai”)

1. CURRENT BACKEND (AS-IS)
--------------------------------------------------------------------------------

  Company ADMIN has:

    • Database Role Permissions   (real source used by API guards)
    • API Authorization           (PermissionsGuard checks request user context)
    • permissions[] intentionally empty on login /auth/me
                                  (shaped for platform-nav only)

  Current flow:

    Login
      ↓
    JWT  { roleCode: "ADMIN", ... }   ← permissions NOT embedded in JWT body
      ↓
    API Request (+ session / user-context cache)
      ↓
    Backend loads role permissions from database
      ↓
    Authorization succeeds
      ↓
    API returns 200


2. ANALYSIS
--------------------------------------------------------------------------------

  From a security perspective, the backend is correct.

  The backend remains the final source of authorization.

  However, the backend currently EXPOSES a different contract than it
  ENFORCES.

  Example today:

    Visible (/auth/me permissions[])     Hidden (DB role → API guard)
    ---------------------------------    ------------------------------
    permissions: []                      branches:view
                                         branches:create
                                         departments:view
                                         custom_fields:view
                                         users:view (if granted)
                                         roles:view (if granted)
                                         ...

  This creates two sources of truth:

    One visible  → FE / QA / docs look at permissions[]
    One hidden   → API guards look at DB-loaded role permissions

  That mismatch caused confusion on Organization APIs (FE thought ADMIN
  had zero org perms because permissions[] was empty, while DB already
  had branches:* after the seed fix).


3. PRODUCT / FE RECOMMENDATION (FROM REVIEW DOC)
--------------------------------------------------------------------------------

  Return explicit TENANT permissions inside the auth snapshot
  (login + /auth/me permissions[] — and optionally JWT claims later).

  Include examples like:

    branches:view | branches:create | …
    departments:view | …
    designations:* | warehouses:*
    users:view | roles:view
    vendors via product modules / supply-chain actions
    custom_fields:view | custom_fields:create | …

  Do NOT return PLATFORM permissions to Company ADMIN:

    companies:create
    plans:create / plans:edit
    modules:create / modules:edit
    subscriptions:create
    (anything that belongs only to Platform Owner)

  Recommended identity flags:

    {
      "roleCode": "ADMIN",
      "tenantAdmin": true,
      "platformOwner": false,
      "permissions": [ "...tenant codes..." ]
    }


4. BENEFITS
--------------------------------------------------------------------------------

  • One authorization contract (visible = same codes FE cares about)
  • Easier FE implementation (hide/show Organization tabs from list)
  • Easier QA (assert permissions[] contains branches:view)
  • Easier documentation
  • Easier debugging
  • Easier future mobile clients

  Important:

    Backend must ALWAYS remain the final authorization layer.
    Frontend permissions NEVER replace API authorization.

10. ARCHITECTURE REVIEW FEEDBACK (APPENDED 2026-07-24)
--------------------------------------------------------------------------------

  Source: Backend Review Feedback — Solution Architecture Opinion
  Rating: ★★★★★ 9.5 / 10
  Verdict: AGREE — approve Hybrid as long-term direction

  --- What the review AGREES with ---

  1. Backend remains the final security layer
     Frontend permissions never replace Backend validation.
     Every protected request must pass server-side permission checks.

  2. Company ADMIN should receive tenant permissions in permissions[]
     Examples: branches:view, departments:view, users:view, roles:view,
     custom_fields:view, …
     Removes ambiguity for FE, QA, docs, and future mobile.

  3. Platform Owner permissions stay separate
     Never on Company ADMIN:
       companies:create, plans:create/update, modules:create,
       subscriptions:create

  4. API Guards should not change
     This is an authentication CONTRACT improvement only.
     Security enforcement stays identical.

  --- Optional suggestions (NOT required for v1) ---

  S1  Future capabilities object (instead of only two booleans):
        capabilities: {
          tenantAdmin, platformOwner,
          canManageOrganization, canManageUsers, canManageRoles
        }
      Optional later — not required for Version 1.

  S2  One centralized Permission Service for all permission generation:
        Role → Role Permissions → Permission Service
          → JWT/Login → /auth/me → API Guards
      Avoid building permission lists in multiple places.

  S3  Keep model flexible for future scopes
      (company → branch / warehouse / department) without redesign.

  --- What the review would NOT change ---

  ✗ Empty permissions[] for Company ADMIN
  ✗ Trusting Frontend permissions for security
  ✗ Removing Backend API Guards
  ✗ Mixing Platform Owner perms into Company ADMIN
  ✗ Special FE exceptions using isCompanyAdmin everywhere

1) PRE-FLIGHT (DO THIS FIRST)
--------------------------------------------------------------------------------

Backend stopped, then from repo root (c:\ERP-Backend):

  1. npx prisma generate
       - Do NOT use PRISMA_GENERATE_NO_ENGINE=1 with normal postgresql:// URLs
       - If EPERM on query_engine DLL → Nest is still locking the file; stop it

  2. npx prisma migrate deploy
       - Expect Security Org V1 tables:
           permission_sets, permission_set_permissions, role_permission_sets
           data_access_policies, data_access_policy_scopes, user_data_access_policies

  3. Start BE:  npm run start:dev
       - Swagger opens; no prisma:// URL errors on login

  4. Start FE (usual command)

  5. Login as company ADMIN, then LOG OUT and LOG IN again
       - First login after migrate seeds catalog + backfills ADMIN with:
           data_access_policies:view|create|edit|delete
           permission_sets:view|create|edit|delete  (catalog only; FE UI removed)
       - Re-login refreshes JWT / permissions[] session

DEMO accounts (if using seed:client-logins):

TEST A — ACCESS POLICIES TAB (PRIMARY FE PATH)
================================================================================

Prep
  - Org data exists: at least 2 warehouses (and optionally branch / department)
  - Logged in as ADMIN with data_access_policies:* codes

Steps
  A1. Open company detail → ?tab=access-policies
      EXPECT: tab loads (not gate / 403 message)

  A2. Create policy
      name: "WH North only"
      scopes: [{ scopeType: "warehouse", scopeId: "<warehouseId-A>" }]
      EXPECT: 201/success; row appears in list

  A3. Get / edit policy
      Change name or add second warehouse scope
      EXPECT: PATCH succeeds; list/detail shows new scopes

  A4. List policies
      EXPECT: GET list returns created policies for THIS company only

  A5. Delete policy (use a disposable one, not one assigned to a critical user)
      EXPECT: DELETE succeeds; gone from list

API (Swagger or FE network)
  GET    /api/v1/companies/:companyId/data-access-policies
  POST   /api/v1/companies/:companyId/data-access-policies
  GET    /api/v1/companies/:companyId/data-access-policies/:id
  PATCH  /api/v1/companies/:companyId/data-access-policies/:id
  DELETE /api/v1/companies/:companyId/data-access-policies/:id

Create body example:
  {
    "code": "WH_NORTH",
    "name": "WH North only",
    "description": "Pilot scope",
    "isActive": true,
    "scopes": [
      { "scopeType": "warehouse", "scopeId": "123" }
    ]
  }

scopeType allowed: branch | department | warehouse

TEST D — ITEMS WAREHOUSE SCOPE PILOT (READ + WRITE)
================================================================================

Prep
  - User U has policy scoped to warehouse A only (not warehouse B)
  - Item I has (or can have) stock rows for warehouse A and B
  - Login as user U (not ADMIN — ADMIN may be unrestricted depending on policies)

D1. READ filter
  Login as U → open Item I detail
  EXPECT: warehouseStock shows only warehouses in scope (A)
           warehouse B stock hidden/filtered when user has warehouse scope policies

  Note: If user has NO policies assigned, BE does not filter (full list).
        Scope filter applies when resolveUserDataScope returns warehouseIds.

D2. WRITE deny (out of scope)
  As U, PUT stock for warehouse B (or delete stock for B)
  API:
    PUT    /api/v1/companies/:companyId/items/:id/warehouses
    DELETE /api/v1/companies/:companyId/items/:id/warehouses/:warehouseId
  EXPECT: 403
           FE toast shows BE deny message (getApiErrorMessage)

D3. WRITE allow (in scope)
  As U, PUT/update stock for warehouse A
  EXPECT: 200/success

D4. ADMIN without restrictive policy
  As ADMIN with no user policies (or full access)
  EXPECT: can read/write all warehouses (baseline control)

LOGIN / ME RESPONSE — WHAT FE MUST READ
--------------------------------------------------------------------------------

  Top level (unchanged shape):

    permissions: string[]          ← primary authz for nav + screens
    tenantAdmin: boolean
    platformOwner: boolean
    mustChangePassword: boolean
    user: { userId, username, displayName, email }
    companies: [...]
    activeCompany: { ... }

  activeCompany.role  — REQUIRED for workspace (NOT null for seeded users)

    {
      "roleId": "123",
      "roleCode": "VENDOR",              // or INVENTORY_ADMIN, ADMIN, …
      "roleName": "Vendor User",
      "systemTemplateKey": "VENDOR",     // use for scoped UX / post-login route
      "roleType": "SYSTEM",
      "isSystem": true
    }

    FE routing priority:
      1. systemTemplateKey (stable across tenants)
      2. roleCode (fallback)

  activeCompany.modules  — workspace entitlement + module-level actions

    [
      {
        "moduleId": 11,
        "moduleCode": "supply-chain",
        "moduleName": "Supply Chain",
        "isActive": true,
        "lifecycleStatus": "AVAILABLE",
        "permissions": ["view", "create", "edit", "delete"]
      }
    ]

    Notes:
      - moduleCode "supply-chain" = company entitled to Supply Chain product
      - permissions[] = Phase-1 module actions (view/create/edit/delete/approve)
      - lifecycleStatus: AVAILABLE | DEPRECATED (show) | DEVELOPMENT (hide nav)
      - Vendors/Items screen access uses flat permissions[] (vendors:* / items:*),
        NOT supply-chain:view alone

  activeCompany.subscription  — unchanged

    { "status": "active" | "trial" | "none", "planCode", "planName", ... }


PERMISSION CODES — NAMING
--------------------------------------------------------------------------------

  Format: resource:action  (same as users:view, roles:edit)

  Supply Chain resources (module entitlement = supply-chain):

    vendors:view | vendors:create | vendors:edit | vendors:delete | vendors:approve
    items:view   | items:create   | items:edit   | items:delete   | items:approve

  Do NOT use:
    supply_chain.vendors.view   (not in this backend)
    permission DB ids for authz

  Legacy (still accepted by BE guards during migration):

    supply-chain:view | create | edit | delete | approve

    Maps to BOTH vendors + items for API checks only.
    Prefer vendors:* / items:* in new FE code.


INDEPENDENCE RULE (CRITICAL)
--------------------------------------------------------------------------------

  vendors:view does NOT grant items:view.
  items:view does NOT grant vendors:view.

  Role matrix must allow selecting Vendors vs Items separately.


FE NAV + SCREEN GATES
--------------------------------------------------------------------------------

  | Screen / action      | Check permission        | Also require                    |
  |----------------------|-------------------------|---------------------------------|
  | Vendors list/detail  | vendors:view            | supply-chain in modules[]       |
  | Create vendor        | vendors:create          | same                            |
  | Edit vendor          | vendors:edit            | same                            |
  | Delete vendor        | vendors:delete          | same                            |
  | Items list/detail    | items:view              | supply-chain in modules[]       |
  | Create item          | items:create            | same                            |
  | Edit item            | items:edit              | same                            |
  | Delete item          | items:delete            | same                            |

  can("vendors:view") example:

    permissions.includes("vendors:view")
    OR permissions.includes("supply-chain:view")   // legacy fallback only

  Module entitlement check (subscription):

    activeCompany.modules.some(m => m.moduleCode === "supply-chain" && m.isActive)

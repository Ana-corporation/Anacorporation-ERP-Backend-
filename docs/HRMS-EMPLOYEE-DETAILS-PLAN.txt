1. DESIGN RULES
---------------
- Two records: users (login, preferences) and employees (HR data).
  employees.user_id is nullable (shop-floor worker with no login) and
  users.employee_id is nullable (external auditor with no HR record).
  TODAY: only employees.user_id exists. Add users.employee_id (nullable
  FK) OR keep the inverse only and treat "no HR record" as
  employees.user_id IS NULL. Do not keep three copies of the emp code
  (employees.employee_code, user_companies.employee_id string, users).
- Every table has company_id. Employee data is scoped by company, and
  optionally by legal entity / branch.
- No country columns on core tables. National IDs, tax and statutory
  numbers go in employee_identifiers (type, value, country, validity).
- Addresses use region / postal code / country_code, never state / PIN only.
- Anything that changes over time is effective-dated (designation,
  department, manager, grade, salary, location, shift).
- Sensitive data: encrypted at rest where needed (bank, ID numbers),
  masked on screen (XXXX1234), view and change audited.
- Collect only what is used (privacy laws). Mark fields optional per
  country in configuration.
- Custom Fields must be available on every section.
- Soft delete only. Exit uses status + dates, never physical delete.
  Anonymize after the retention period.

28. ERP INTEGRATION (HRMS is a module inside the ERP)
-----------------------------------------------------
  28.1 One employee record, used everywhere
    ERP module           Uses from the employee record
    Sales Quotation      Salesperson, approver, reporting manager
                         (approval chain)
    Inventory / Store    Assigned store / location, store-keeper, who
                         issued or received (GRN, Material Issue)
    Production           Shop-floor workers, shift, skills and
                         certifications (welding, forklift), work centre
    Purchase             Buyer, approver limits, department
    Finance              Cost center, department costing, payroll expense
    Approvals (all)      Reporting manager, designation, department,
                         delegate
    Audit log            Which person did the action
    Permissions          Role and data scope (own, team, branch, company)

  28.2 REQUIREMENT: one Employee page, all fields apply to HRMS and ERP
    There is ONE Employee page (Employee master) with every field and
    section in this plan. It is the single source for the HRMS and for
    the ERP modules. There is no separate "ERP employee" and "HR employee",
    and no field is reserved for only one side.
      - Every field is stored once, on the one employee record.
      - HRMS screens (leave, attendance, payroll, exit) read it.
      - ERP screens (quotation, store, production, purchase, approvals)
        read the same record.
      - Page layout: tabs for the sections (Core, Personal, Contact,
        Address, Employment, Assignment, Schedule, Compensation,
        Identifiers, Bank, Education, Experience, Skills, Documents,
        Assets, Health, Exit ...).
    Who sees which field is controlled by PERMISSION, not by splitting
    the record:
      - Normal fields (name, department, designation, location, manager,
        shift, skills): visible to anyone with employees:view.
      - Sensitive fields [S] (compensation, bank, identifiers, date of
        birth, medical): need the sensitive permissions in section 26,
        shown masked otherwise.
    Which tabs and fields a company uses is controlled by Form
    Configuration and Tab Access, so a company that does not use payroll
    simply hides those tabs.

  28.3 Rules
    1. One master per thing: Department, Designation, Branch, Cost Center
       and Location exist once, used by both HRMS and ERP.
    2. Link by ID, never by name: a quotation stores
       salesperson_employee_id, a GRN stores received_by_employee_id.
    3. Selectors in ERP screens use a light lookup API
       (GET /employees/lookup: id, code, name, department, designation,
       status). It never returns sensitive fields.
    4. Exit flow: when status becomes Exited, the login is deactivated,
       and open approvals, tasks, quotations (salesperson) and store
       assignments are listed for reassignment. History keeps the old
       name through snapshots.
    5. Same page, same fields for every company. A company that uses only
       the ERP hides the tabs it does not need (for example payroll) with
       Form Configuration and Tab Access. The data model never changes
       and no code branches per module.
    6. Same user, role and permission model across ERP and HRMS.
    7. Employee data scope in ERP lists follows the user's data scope
       (own, team, branch, company).
    8. Master data for approvals (limits per designation or grade) lives
       in the ERP approval rules and reads designation / grade from here.

  28.4 Build dependency
    The Employee page is built with ALL fields in the planned phases.
    ERP modules need sections 2, 7 and 8 (core, employment, assignments)
    and the Department, Designation, Branch and Cost Center masters first,
    because they use a salesperson, approver, store-keeper or worker.
    The remaining tabs are built in the phases of section 27, on the same
    page and the same table design.

  28.5 For ANA
    ANA uses the same Employee page. In Form Configuration and Tab
    Access, start with the tabs ANA needs now (Core, Employment,
    Assignment, Schedule, Skills) and show the other tabs when ANA
    enables the HRMS features. No new fields or tables are added later.
